# Utgifter (expenses) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let any admin record an expense (utgift) against a Bolig — optionally tied to a Delprosjekt — with category, supplier, amount, who paid (an owner personally, or the property's driftskonto), and an optional receipt image, and let the Delprosjekter page show "faktisk" spend against each delprosjekt's "planlagt" budget.

**Architecture:** Mirrors the existing Kapitalinnskudd feature end to end: a `Utgift` Prisma model, a `lib/utgift.ts` data-access module (create/list/sum/delete), server actions under the Delprosjekter route, and a panel component rendered on the existing `boliger/[id]/delprosjekter` page. Receipt images are stored as `Bytes` directly on the `Utgift` row (same SQLite/Turso database everything else uses) and are handled by a two-phase flow: the server action creates the expense's metadata row (small JSON payload), and a separate authenticated API route accepts the binary receipt upload via `multipart/form-data` and attaches it to that row afterward — mirroring the transport `app/api/upload/route.ts` already uses successfully, but **not** that endpoint's storage destination, which is unsuitable for private financial documents (see "Receipt storage" below).

**Tech Stack:** Next.js 16 App Router server actions + Route Handlers, Prisma 7 + libsql, Vitest + `vi.hoisted` prisma mocking (existing patterns in `lib/kapitalinnskudd.ts`, `lib/timeregistrering.ts`, `app/admin/(protected)/boliger/[id]/delprosjekter/actions.ts`, `app/api/boliger/[id]/route.ts`).

**Spec:** `docs/superpowers/specs/2026-10-25-eiendomsplattform-design.md` §7.4 (Utgifter), with the "driftskonto" clarification in that same section, and the pre-existing §7.3/§7.5 implementations as the structural precedent.

## Global Constraints

- Money fields are `Int` (whole kroner, no decimals) — matches `Kapitalinnskudd.belop`, `Bolig.pris`, `Delprosjekt.budsjett`.
- Dates are submitted from the client as `YYYY-MM-DD` strings and parsed server-side with the exact `dato`/`Number.isNaN`/round-trip validation already used in `registrerInnskuddAction` (`app/admin/(protected)/boliger/[id]/kapital/actions.ts:20-24`) and `registrerTimerAction` (`app/admin/(protected)/boliger/[id]/delprosjekter/actions.ts:34-40`) — copy that exact pattern, do not re-derive it.
- All server actions require a session (`getServerSession(authOptions)`; throw `"Ikke autorisert."` if absent), per existing convention. The receipt API route (Task 3) uses `krevInnloggetSesjon()` instead, matching `app/api/upload/route.ts`'s own convention for Route Handlers (the two helpers are both pre-existing; use whichever one the file's sibling code already uses).
- Any logged-in admin (not just the four `rolle: "eier"` rows) may create or delete an Utgift. Deletion has **no ownership restriction** — same rationale as `slettKapitalinnskudd`: this is shared company bookkeeping (any co-owner may correct a misrecorded expense), not a personal log like Timeregistrering.
- `betaltAvBrukerId` is nullable: `null` means "driftskonto" (paid from the property's pooled capital — no individual is credited), a non-null value is the `AdminUser.id` of the owner (`rolle: "eier"`) who personally laid the money out. This is the plan's own design call, resolving the spec's "person eller driftskonto" into a single nullable FK instead of a separate boolean flag.
- `delprosjektId` is nullable: an expense may be tied to a specific delprosjekt's budget, or be a property-level cost with no delprosjekt (e.g. a municipal fee). When set, it must reference a delprosjekt belonging to the same `eiendomId` — mirror the existing cross-check in `registrerTimerAction` (`app/admin/(protected)/boliger/[id]/delprosjekter/actions.ts:50-53`).
- `kategori` is a required free-text field (no enum — the spec does not pin a fixed category list, so inventing one would be a requirement not in the spec). `leverandor` and `beskrivelse` are optional free text.
- **Any query that lists `AdminUser` rows for display (e.g. the "betalt av" dropdown's owner list, or a joined lookup of who paid) MUST `select` only `{ id: true, navn: true }`.** Never pass a full `AdminUser` record (which includes `passord`, the bcrypt hash) down into a client component's props or into a nested relation include — this is exactly how `app/admin/(protected)/boliger/[id]/kapital/page.tsx:65` already does it for the top-level fetch; copy that, do not re-derive a naive `findMany`/relation lookup with no `select`.
- **Receipt storage:** the existing `app/api/upload/route.ts` is not reused for receipts, for two reasons this plan's independent review surfaced: (1) it writes to `public/uploads`, which Next.js serves with no authentication at all — receipts are private financial documents, unlike the public property photos that endpoint currently serves; (2) in a production/serverless deployment, Next.js indexes `public/` at build time and does not serve files written to it afterward, so a receipt uploaded after deploy would 404 forever. Instead: the receipt's bytes are stored directly on the `Utgift` row as a Prisma `Bytes` column (SQLite `BLOB`, same database everything else already uses — no new infrastructure, no new dependency), uploaded and retrieved through a new authenticated route (Task 3).
- **Receipt transport is two-phase, not a single server-action call carrying the image bytes.** Next.js Server Actions have a default 1 MiB request-body ceiling (`experimental.serverActions.bodySizeLimit`, unset in this project's `next.config.ts`), and base64-encoding the bytes to pass them as a string argument would inflate a 4 MB image to over 5 MB — past both that default ceiling and the platform's own request-body limit. So: `registrerUtgiftAction` (Task 2) creates the `Utgift` row with no receipt fields at all and returns its `id`; if the user attached a receipt, the client then `POST`s the raw file as `multipart/form-data` to `app/api/utgifter/[id]/kvittering/route.ts` (Task 3) using that `id` — the same binary-transport mechanism `app/api/upload/route.ts` already uses successfully (Route Handlers read the request body directly; they are not subject to the Server Action body-size config), just writing to the database instead of the filesystem.
- **Receipt content is validated server-side by sniffing the actual bytes, never by trusting the client-supplied MIME type or file extension.** An authenticated admin could otherwise upload an HTML file or a script-bearing SVG with a spoofed `image/*` content type; if another admin's browser later rendered it at the stored (client-asserted) MIME type, it could execute in the context of the application's own origin. `lib/utgift.ts` (Task 1) exports a small magic-byte detector that recognizes JPEG, PNG, GIF, and WebP signatures and rejects everything else — the *detected* format is what gets stored and served as `Content-Type`, never the browser's `file.type`. The receipt GET route additionally sends `X-Content-Type-Options: nosniff` so a browser never re-interprets the response body as something other than the declared image type.
- Receipt uploads are capped at **4,000,000 bytes (~4 MB) raw**, checked server-side before the bytes are stored, with a clear rejection message — chosen to stay safely under the platform's request-body ceiling (Vercel Functions cap request/response bodies at 4.5 MB) with headroom for the small amount of multipart boundary/header overhead around the raw file bytes.
- List queries that return multiple `Utgift` rows (`hentUtgifterForEiendom`) must never select the `kvitteringBilde` bytes column — loading every receipt's raw image bytes into a server-rendered list page would be both slow and pointless when only one receipt is ever viewed at a time. Expose only a `harKvittering: boolean`, derived from whether `kvitteringMimeType` is set (the two columns are always written together). **Use a single top-level `select` that lists every needed scalar field plus nested relation selects for `delprosjekt`/`betaltAvBruker` — Prisma rejects combining `select` and `include` in the same query**, so there is exactly one way to write this query correctly; do not reach for `include` alongside a top-level `select`.

## Review Focus

- A `belop` of 0, negative, or a non-integer (fractional kroner) must be rejected, same bound (`<= 0` or `> 2_147_483_647`) as `registrerInnskuddAction`.
- `delprosjektId` set to a delprosjekt that exists but belongs to a *different* eiendom must be rejected (cross-property leakage), not silently accepted.
- `betaltAvBrukerId` set to a user that exists but is not `rolle: "eier"` must be rejected — only owners can be credited with personally paying.
- Deleting a `Bolig` that still has `Utgift` rows must be blocked with a clear 409, both on the fast path and the race-condition fallback — the existing `DELETE /api/boliger/[id]` handler must learn about this third dependency, not just delprosjekter/kapitalinnskudd.
- The "faktisk" sum per delprosjekt must only include `Utgift` rows that actually have that `delprosjektId` set — property-level expenses with `delprosjektId: null` must not be silently included in every delprosjekt's actual-spend total (and must not vanish from the page either — they need their own display).
- A receipt image must not be retrievable by an unauthenticated request; an oversized upload must be rejected server-side with a clear error rather than crashing or silently truncating; and a non-image payload (HTML, SVG, or anything else that fails the magic-byte check) must be rejected rather than stored and later served back under a spoofed content type.

  - `harUtgifter(prisma: PrismaClient, eiendomId: number): Promise<boolean>`

```ts
export async function GET(_req: NextRequest, { params }: { params: Promise<{ id: string }> }) {
  const bruker = await krevInnloggetSesjon();
  if (!bruker) return NextResponse.json({ error: "Ikke autorisert" }, { status: 401 });

  const { id } = await params;
  const kvittering = await hentKvittering(prisma, parseInt(id));
  if (!kvittering) return NextResponse.json({ error: UTGIFT_FEIL }, { status: 404 });

  return new NextResponse(kvittering.bytes, {
    headers: { "Content-Type": kvittering.mimeType, "X-Content-Type-Options": "nosniff" },
  });
}

export async function POST(req: NextRequest, { params }: { params: Promise<{ id: string }> }) {
  const bruker = await krevInnloggetSesjon();
  if (!bruker) return NextResponse.json({ error: "Ikke autorisert" }, { status: 401 });

  const { id } = await params;
  const formData = await req.formData();
  const file = formData.get("file") as File | null;
  if (!file) return NextResponse.json({ error: "Ingen fil" }, { status: 400 });

  const bytes = Buffer.from(await file.arrayBuffer());

  try {
    await lagreKvittering(prisma, parseInt(id), bytes);
    return NextResponse.json({ ok: true });
  } catch (err) {
    if (err instanceof Error && err.message === UTGIFT_KVITTERING_FOR_STOR) {
      return NextResponse.json({ error: UTGIFT_KVITTERING_FOR_STOR }, { status: 413 });
    }
    if (err instanceof Error && err.message === UTGIFT_KVITTERING_UGYLDIG_FORMAT) {
      return NextResponse.json({ error: UTGIFT_KVITTERING_UGYLDIG_FORMAT }, { status: 400 });
    }
    if (err instanceof Error && err.message === UTGIFT_FEIL) {
      return NextResponse.json({ error: UTGIFT_FEIL }, { status: 404 });
    }
    throw err;
  }
}
```

```ts
async function handleSubmit(e: React.FormEvent) {
  e.preventDefault();
  setLaster(true);
  setFeil("");

  try {
    const resultat = await registrerUtgiftAction({ /* ...fields, no receipt data... */ });
    if (!resultat.ok) {
      setFeil(resultat.feilmelding);
      return;
    }

    // The expense row now exists. Reset the form and refresh the list
    // immediately, regardless of what happens to the receipt below —
    // this is what proves to the user that re-submitting would create
    // a second expense, not retry a failed one.
    resetFormFelter();
    router.refresh();

    if (fil) {
      try {
        const formData = new FormData();
        formData.append("file", fil);
        const res = await fetch(`/api/utgifter/${resultat.data.id}/kvittering`, { method: "POST", body: formData });
        if (!res.ok) {
          let feilmelding = "ukjent feil";
          try {
            feilmelding = (await res.json()).error ?? feilmelding;
          } catch {
            // Non-JSON error body (e.g. an HTML error page) — keep the generic feilmelding.
          }
          setFeil(`Utgiften ble registrert, men kvitteringsbildet kunne ikke lagres: ${feilmelding}`);
        } else {
          // The first refresh (right after creation) ran before this upload
          // finished, so it could not have seen harKvittering: true yet —
          // refresh again now so the "Kvittering" link appears without
          // the admin needing to reload the page themselves.
          router.refresh();
        }
      } catch {
        // Network failure reaching the upload route at all.
        setFeil("Utgiften ble registrert, men kvitteringsbildet kunne ikke lagres (nettverksfeil).");
      }
    }
  } catch {
    setFeil("Noe gikk galt. Prøv igjen.");
  } finally {
    setLaster(false);
  }
}
```

The outer `catch`/`finally` only ever fires for a failure in the *creation* call (`registrerUtgiftAction` itself throwing, e.g. a session error) — at that point nothing was created, so "Noe gikk galt. Prøv igjen." is accurate and safe to act on. Every failure mode after that point (a non-ok response with a parseable JSON error, a non-ok response with an unparseable body, or the `fetch` itself rejecting over the network) is caught by the inner `try/catch` and always produces a message that says the expense *was* saved. `setLaster(false)` still runs via the outer `finally` in every case — this is the same bug the final Timeregistrering review caught and fixed, just with one more failure path to cover now that there are two network calls instead of one.
